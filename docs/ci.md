# GitLab CI/CD operations

## Pipeline structure

```
parent (.gitlab-ci.yml)
  test            alpine; shellcheck + tests/run.sh        (push, MR, manual)
  detect-release  alpine; scripts/detect-release.sh → release.env (dotenv)
  generate        alpine; scripts/ci/generate-job.sh → child-pipeline.yml
  build           trigger: include artifact child-pipeline.yml, strategy: depend
child (generated by tools/platforms.py)
  build:<id>      golang:<go.mod version>-alpine<ALPINE_VERSION>; build, compress, validate
  publish:<id>    alpine; needs build:<id>; upload to Generic Package Registry
  release         alpine; needs this run's publish jobs; GitLab Release + tag
```

All of these GitLab features are available on the Free tier: parent-child
pipelines with `trigger:include:artifact`, dotenv reports, `needs`, caches,
`resource_group`, and pipeline schedules.

The release jobs (`detect-release`, `generate`, `build`) run only for `web`,
`api`, `trigger`, `schedule` and `pipeline` sources. Pushes and merge
requests run `test` only.

## Setup

1. Push this repository to GitLab.
2. Check that the Package Registry is enabled (*Settings › General ›
   Visibility* › Packages). The default `CI_JOB_TOKEN` can publish packages
   to its own project.
3. Optional: add `GITHUB_TOKEN` as a **masked, protected** CI/CD variable
   (a fine-grained token with no scopes is enough). Without it, detection
   uses anonymous GitHub API requests (60/hour per IP), which can be
   exhausted on shared runners.
4. Create a pipeline schedule (*Build › Pipeline schedules*), for example
   daily, on the default branch. Scheduled runs skip `test` and build only
   targets that have not been published.

## Run-time variables

| Variable | Default | Meaning |
|---|---|---|
| `TAILSCALE_VERSION` | (blank) | Build this stable version instead of the newest. Must be a published, non-prerelease GitHub release with an even minor number. |
| `TARGETS` | (blank) | Comma-separated subset of enabled target ids. |
| `FORCE_REBUILD` | `false` | Build even if already published. Identical files are not re-uploaded; changed files are added as new package files (or rejected if duplicates are disabled). |
| `PUBLISH` | `true` | `false` builds and validates only. Artifacts stay downloadable from the job for 2 weeks. |
| `IMAGE_PREFIX` | group Dependency Proxy | Registry prefix for every job image; see [Container images](#container-images). Projects in a personal namespace must set it to `docker.io/library/`. Set it as a CI/CD variable, not per run. |
| `GO_IMAGE` | derived | Full build image reference, used verbatim (must be Alpine-based). |

Detection writes its results as `RELEASE_*` dotenv variables. These are
deliberately different from `TAILSCALE_VERSION`: in GitLab's variable
precedence, a blank manual-run variable would otherwise override a dotenv
value. For the same reason the `build` trigger forwards no variables to the
child pipeline, whose jobs take their inputs from `TT_*` job variables
written by `generate` (`TT_BUILD_VERSION`, `TT_BUILD_COMMIT`,
`TT_TARGET_ID`, `TT_TARGET_CONFIG`, `TT_RELEASE_TARGETS`).

## Container images

No custom image is built. Every job uses an official image and installs
its tools with `scripts/ci/install-deps.sh` (about 10–30 s per job):

| Jobs | Image |
|---|---|
| test, detect-release, generate, publish, release | `${IMAGE_PREFIX}alpine:${ALPINE_VERSION}` |
| build:&lt;target&gt; | `${IMAGE_PREFIX}golang:<go.mod version>-alpine${ALPINE_VERSION}` |

`ALPINE_VERSION` (currently `3.24`) is set once in `.gitlab-ci.yml`, with
the matching script default in `scripts/lib/common.sh`; a test fails if
they differ. Official `golang` images are only published for the two newest
Alpine releases, so `detect-release` checks Docker Hub for the derived tag
and fails early with a clear message when `ALPINE_VERSION` needs raising
(roughly once a year).

### Using the GitLab Dependency Proxy (GitLab Free)

The Dependency Proxy caches Docker Hub images inside GitLab, which avoids
Docker Hub pull rate limits on shared runners and keeps builds working if
Docker Hub is briefly unavailable.

1. **Put the project in a group.** The proxy works per group; it is not
   available to projects in a personal namespace. If needed, create a group
   and use *Settings › General › Advanced › Transfer project*.
2. **Check that the proxy is on.** In the group: *Settings › Packages and
   registries › Dependency Proxy › Enable Proxy* (on by default; changing it
   requires the Owner role).
3. **Optional: add Docker Hub credentials.** In the same section, under
   *Docker Hub authentication*, enter a Docker Hub username and a personal
   access token (read-only public repository access is enough). Without
   them, the proxy pulls from Docker Hub anonymously, but cache hits still
   avoid most pulls.
4. **Nothing to configure in the project.** For a project in a group,
   `.gitlab-ci.yml` sets `IMAGE_PREFIX` to
   `$CI_DEPENDENCY_PROXY_DIRECT_GROUP_IMAGE_PREFIX/` through its workflow
   rules (the proxy of the group that directly contains the project).
5. **Run a pipeline and check the job logs.** The first lines should show
   `Pulling docker image <gitlab host>:443/<group path>/dependency_proxy/containers/alpine:3.24`.
   Cached images are listed under the group's *Operate › Dependency Proxy*.

Runners log in to the proxy automatically, so no token is needed in the
pipeline. To override the default, add a project CI/CD variable
`IMAGE_PREFIX` (*Settings › CI/CD › Variables*; not protected, not masked):
`docker.io/library/` pulls from Docker Hub directly, and
`$CI_DEPENDENCY_PROXY_GROUP_IMAGE_PREFIX/` uses the top-level group's proxy
instead. Project variables take precedence over the workflow rule.

**Projects in a personal namespace must set `IMAGE_PREFIX`.** The Dependency
Proxy only exists for groups, but GitLab still sets
`CI_DEPENDENCY_PROXY_DIRECT_GROUP_IMAGE_PREFIX` (to
`<host>:443/<username>/dependency_proxy/containers`), and pipelines can't
tell the two cases apart. Without the variable, every job fails to pull its
image with a 404 page. Set `IMAGE_PREFIX` to `docker.io/library/`.

## Releases and tags

The `release` job (`scripts/release.sh`) runs whenever publishing is on,
including runs where every target was already published:

- It acts only when **every enabled target** is published for the version
  and commit. Otherwise it logs which targets are missing and exits
  successfully; a later run creates the Release. A failing target therefore
  delays the Release for all targets, while its packages for the other
  targets are still published.
- It creates the Release and tag `v<version>` at the pipeline's commit
  through the Releases API using `CI_JOB_TOKEN`. If `v*` tags are protected,
  the user who runs or owns the schedule must be allowed to create them.
- Asset links point at the package files and get version-independent
  `filepath`s (`/linux_arm64.upx`, `/linux_arm64.manifest`, …), so
  `-/releases/permalink/latest/downloads/<filepath>` always resolves to the
  newest Release.
- GitLab treats the most recently released Release as latest. To keep that
  equal to the highest version, no Release is created for a version older
  than the newest existing Release (for example, a manual rebuild of an old
  version). Its packages are still published.
- When a Release already exists (for example after enabling a new target),
  missing links are added and the notes are refreshed. Existing links are
  never removed.
- `resource_group: release` serialises Release updates across pipelines.

## Skip and retry semantics

- `check-published.sh` treats `<base>.metadata.json` as the completion
  marker. `publish.sh` uploads it **last**. Partial uploads, such as a job
  killed mid-upload, read as "not published", and the next run rebuilds and
  re-publishes that target.
- Before each upload, `publish.sh` downloads any existing file with that name
  and skips it if the SHA-256 matches. After each upload it reads the file
  back to verify it. Retries therefore send only what is missing. Builds are
  reproducible (same toolchain, `-trimpath`, pinned source), so re-built files
  normally match byte for byte.
- If a group disables duplicate generic packages and a *different* file with
  the same name exists, publishing fails with an explanatory error instead of
  overwriting it.
- `publish:<id>` uses `resource_group: publish-<id>`, so two pipelines never
  publish the same target at once.
- Failing targets never block or mark other targets. Each `publish:<id>`
  depends only on its own `build:<id>`.
- Transient runner failures are retried once. Network operations use curl
  retries.

## Caching

- `.cache/go-mod` (key `gomod-v1`): Go module cache, shared across targets
  and versions. It is safe because modules are verified against `go.sum`.
- `.cache/go-build` (key `gobuild-<id>-v1`): Go build cache per target. Go
  trims entries unused for 5 days.

Change the `-v1` suffixes in `tools/platforms.py` to invalidate the caches.

## Resource use on GitLab Free

This has not been measured on GitLab.com runners yet. As a local reference,
a cold linux/arm64 build in Docker (module download, compile, UPX `--best
--lzma`, QEMU tests) took well under a minute on a workstation. Expect several
times that on a small shared runner. Scheduled runs with nothing new to build
use only the `detect-release` and `generate` jobs plus the child pipeline's
`release` job, which confirms the Release is up to date (about a minute in
total on a self-hosted runner).

## Public GitHub releases

Run **Publish Tinyscale Release** from the Actions tab on the default
branch to publish the latest stable upstream version. The separate
**Check for New Tailscale Releases** workflow runs daily at 05:17 UTC and
can also be run manually. Both use the same check and release workflow.
When the version is already published, the check skips the build jobs.

GitHub build jobs share a Go module cache across targets and runs. Each
target also has its own Go compiler cache, scoped to the Go image and
upstream commit.

The release workflow reuses the parallel CI builds. After all targets pass,
it verifies the artifacts, uploads them to a draft, and checks each uploaded
asset before publishing it as latest. Devices use stable manifest asset
names such as `linux_arm64.manifest` and the versioned binaries named in
those manifests. The publish job uses GitHub's built-in token.

If an upload fails, rerun the workflow at the same source commit to resume
the draft. A published release or a draft tied to another source commit
requires manual review before changing any of its assets.
